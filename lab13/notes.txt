------------------------------------------------------------------------
Observe
------------------------------------------------------------------------

1. Without the lock, why do the letters mix? (How many system calls does
   one line cost?)

   One line costs 31 system calls: lines() calls write(1, p, 1) once for
   every character, 30 letters plus the '\n'. The kernel makes each single
   write() whole, but nothing keeps the 31 writes of one line together.
   make qemu starts xv6 with 3 CPUs, so the two processes really run at the
   same time on different CPUs, and the scheduler can also switch between
   them after any system call. Between two writes of process A, process B
   can do one or more writes of its own, so the letters of the two lines
   interleave ("AbAbAb..."), and how they interleave changes from run to run.

2. With the lock every line is whole. Which two lines of mix.c make one line
   a critical section?

       if (uselock)
         sem_down(3);          // before the loop that writes the line
       ...
       if (uselock)
         sem_up(3);            // after the loop

   Semaphore 3 starts at 1 (sem_init(3, 1) in main), so it works as a lock:
   sem_down(3) lets only one process at a time into the loop of 31 writes,
   and sem_up(3) lets the other one in only after the whole line, '\n'
   included, has been written.

3. In sem_down the test is "while (s->value == 0)", not "if". Why can a
   process wake up and still find 0?

   - sem_up calls wakeup(s), and wakeup wakes EVERY process that sleeps on
     the address s, not just one. sem_up added only one unit. The first
     woken process to take s->lock takes it and the value is 0 again, so
     the others wake up and find 0.
   - Between wakeup() and the moment the woken process runs again and takes
     s->lock, a third process that was not sleeping can call sem_down,
     find value 1 and take the unit first.
   - A process can also leave sleep() for a reason that has nothing to do
     with the semaphore: kkill() makes a SLEEPING process RUNNABLE so that
     it can notice it was killed. sem_down checks killed() for exactly this
     case.
   With "while", the process checks the value again after every wakeup and
   goes back to sleep if it is still 0. With "if", it would do
   s->value-- on 0, the value would become -1, and two processes could be
   in the critical section at the same time.

4. sem_down calls release(&s->lock) BEFORE sleep(). What would go wrong if
   it slept holding the spinlock?

   The process that must wake it up can never run sem_up: sem_up starts with
   acquire(&s->lock), which would spin forever on another CPU, because the
   sleeper holds that lock and will not release it until it is woken. The
   sleeper waits for sem_up and sem_up waits for the sleeper: a deadlock.
   Every later sem_init/sem_down/sem_up on that semaphore would also spin
   forever. A spinlock also turns interrupts off on its CPU (push_off), and
   xv6 refuses to switch away while holding any lock other than p->lock:
   sched() checks "mycpu()->noff != 1" and the kernel would panic with
   "sched locks".
   Releasing the lock before sleep() does not lose a wakeup, because
   sleep_prepare(s) already set p->chan = s. If sem_up runs between
   release() and sleep(), wakeup(s) clears p->chan, and sleep() sees
   p->chan == 0 and returns at once instead of sleeping.

Optional: sem_trydown (number 27)
------------------------------------------------------------------------
Like sem_down, but if the value is 0 it returns -1 at once instead of
sleeping (kernel/sem.c: sys_sem_trydown; test: user/trytest.c).

$ trytest
value 1: sem_trydown(4) = 0   (took the unit)
value 0: sem_trydown(4) = -1  (nothing to take, did not sleep)
after sem_up(4): sem_trydown(4) = 0
