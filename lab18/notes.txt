------------------------------------------------------------------------
Part 1: the switch (the three TODO places)
------------------------------------------------------------------------
1) struct context: the 14 callee-saved registers, each uint64, in the same
   order as the offsets used in uthread_switch.S:

     ra (0), sp (8), s0 (16), s1 (24), ... s11 (104)

2) thread_create: the new thread has never run, so its context is built by
   hand. The stack grows down, so sp starts at the END of the stack array:

     memset(&t->ctx, 0, sizeof(t->ctx));
     t->ctx.ra = (uint64)func;                      /* where to "return"   */
     t->ctx.sp = (uint64)(t->stack + STACK_SIZE);   /* top of own stack    */

   (STACK_SIZE = 8192 is a multiple of 16 and the stack is aligned(16), so
   sp is 16-byte aligned, as the RISC-V calling convention requires.)

3) thread_schedule: when another thread is chosen

     struct thread *old = current_thread;
     next_thread->state = RUNNING;
     current_thread = next_thread;
     thread_switch(&old->ctx, &next_thread->ctx);

   current_thread is changed BEFORE the switch, because after the switch the
   code that runs is the other thread's, and it must already see itself as
   current.

The three threads take turns exactly as expected: after the start-up
("started" for a, b, c), every thread prints one number and yields, and the
round-robin order is c, a, b. Each one counts to 99 ("exit after 100"), and
when all three are FREE, thread_schedule finds no runnable thread and exits.

Why c prints first: main switches to a, which prints "started", sets
a_started and yields (b and c have not started yet) to b. b does the same and
yields to c. When c starts, a_started and b_started are already 1, so c skips
its while loop, prints "thread_c 0" and yields. Only now do a and then b
re-check their while loops, find all three flags set, and print their 0.
From there on the round-robin order c, a, b repeats.


------------------------------------------------------------------------
Observe: what exactly does thread_switch save and load? Why is ra the
register that makes execution continue in the other thread?
------------------------------------------------------------------------
thread_switch(old, new) saves 14 registers of the running thread into
*old (a0): ra, sp and s0..s11, and then loads the same 14 registers from
*new (a1). These are exactly the callee-saved registers of the RISC-V
calling convention, plus ra and sp.

It does not need to save anything else:
  - thread_switch is called like a normal C function, so the compiler
    already assumes that the caller-saved registers (t0-t6, a0-a7) are
    destroyed by the call and saved them on the stack itself if it needed
    them;
  - the local variables of the thread live on its own stack, which is not
    copied: it is enough to switch sp to point into the other stack;
  - pc is not saved explicitly, because the place where the thread stopped
    is already in ra (the return address of the call to thread_switch).

Why ra: the last instruction of thread_switch is "ret", which is just
"jump to the address in ra". thread_switch was CALLED by the old thread, but
before ret it loads ra (and sp) of the NEW thread. So ret does not return to
the caller; it returns into the new thread:
  - if the new thread has run before, its saved ra is the instruction after
    its own call to thread_switch (inside thread_schedule), so it continues
    there, on its own stack (the restored sp), as if its call had just
    returned;
  - if the new thread has never run, its ra is the function set by
    thread_create (thread_a, thread_b or thread_c), so ret jumps to the
    beginning of that function, with sp at the top of its fresh stack.

So ra decides WHERE execution continues and sp decides ON WHICH STACK; the
s registers give back the values the thread's compiled code expects to
find. This is the same thing that the kernel's swtch does between a process
and the scheduler, but here it happens entirely in user space, without any
system call and without the kernel knowing that there are threads.

What goes wrong without the right ra/sp in thread_create: with ra = 0 the
first ret jumps to address 0 (the start of the program, or a page fault),
and with sp = 0 or the bottom of the stack the first push writes outside the
thread's stack and destroys other memory (for example the context or the
stack of the previous thread).
